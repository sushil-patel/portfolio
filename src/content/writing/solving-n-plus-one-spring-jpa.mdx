When building **Claimora**, our mock insurance claims processing backend, an early load test on the claims list endpoint revealed a classic ORM performance trap: querying a single page of 20 claims triggered **21 separate SQL queries**.

Under concurrent recruiter or user traffic, this query amplification rapidly exhausts database connection pools, saturates network sockets, and spikes p99 response times.

In this article, I analyze why the N+1 problem occurs, why changing `FetchType.LAZY` to `FetchType.EAGER` makes the problem worse, and how to resolve it cleanly using **`@EntityGraph`** and **DTO Projections**.

---

## 1. The Anatomy of an N+1 Query Failure

Consider a standard relational relationship where each `Claim` has many `ClaimDocument` entities:

```java
@Entity
@Table(name = "claims")
public class Claim {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String claimNumber;

    @OneToMany(mappedBy = "claim", fetch = FetchType.LAZY)
    private List<ClaimDocument> documents = new ArrayList<>();
}
```

When invoking `claimRepository.findAll(pageable)`, Hibernate issues 1 query:

```sql
-- Query 1: Fetch paginated claims
SELECT c.id, c.claim_number FROM claims c LIMIT 20 OFFSET 0;
```

However, as soon as the service layer iterates through the results or transforms the entities into a `ClaimResponse` DTO:

```java
return claims.map(claim -> new ClaimResponse(
    claim.getId(),
    claim.getClaimNumber(),
    claim.getDocuments().size() // Triggers proxy initialization!
));
```

Hibernate realizes that the `documents` collection is uninitialized. For *each* of the 20 claims, it pauses and fires an individual lookup:

```sql
SELECT d.id, d.file_name, d.claim_id FROM claim_documents d WHERE d.claim_id = 1;
SELECT d.id, d.file_name, d.claim_id FROM claim_documents d WHERE d.claim_id = 2;
...
SELECT d.id, d.file_name, d.claim_id FROM claim_documents d WHERE d.claim_id = 20;
```

**Total Queries:** 1 initial query + N subqueries = **21 queries for 20 records**. If your page size is 100, you execute 101 queries!

## 2. The False Panacea: Why `FetchType.EAGER` is Harmful

A common rookie mistake is flipping `fetch = FetchType.EAGER`:

```java
// ANTIPATTERN: Do NOT do this
@OneToMany(mappedBy = "claim", fetch = FetchType.EAGER)
private List<ClaimDocument> documents;
```

This is dangerous for two reasons:

1. **JPQL `findAll()` Still Executes N+1 Queries:** Under the JPA specification, JPQL queries (`SELECT c FROM Claim c`) do not automatically rewrite into joins; Hibernate simply issues the initial query and then immediately issues N secondary queries eagerly before returning.
2. **Global Query Contamination:** Every single use case that retrieves a `Claim` (such as a lightweight status update or audit check) is now forced to fetch the entire document tree, loading megabytes of unneeded memory into the Hibernate session.

---

## 3. Solution 1: Dynamic Fetching with `@EntityGraph`

The idiomatic JPA solution is **declarative entity graphs**, which instruct Hibernate to fetch the relationship in a single SQL `LEFT OUTER JOIN` **only for the specific repository query**:

```java
public interface ClaimRepository extends JpaRepository<Claim, Long> {

    @EntityGraph(attributePaths = {"documents", "policy"})
    @Query("SELECT c FROM Claim c WHERE c.status = :status")
    Page<Claim> findAllWithDetails(@Param("status") ClaimStatus status, Pageable pageable);
}
```

### The Generated SQL

```sql
SELECT 
    c.id, c.claim_number, c.status,
    d.id, d.file_name, d.claim_id,
    p.id, p.policy_number
FROM claims c
LEFT OUTER JOIN claim_documents d ON c.id = d.claim_id
LEFT OUTER JOIN policies p ON c.policy_id = p.id
WHERE c.status = 'UNDER_REVIEW'
LIMIT 20 OFFSET 0;
```

**Result:** **1 single query** retrieves the claims and all associated documents and policy headers. Connection pool round-trips drop by over 90%.

## 4. Solution 2: Read-Only DTO Projections

If an endpoint only needs summary metrics for a dashboard (e.g. claim number, status, and total amount), loading managed JPA entities with dirty checking and entity graphs is unnecessary overhead.

Spring Data JPA allows us to query directly into lightweight interfaces:

```java
public interface ClaimSummary {
    Long getId();
    String getClaimNumber();
    String getStatus();
    BigDecimal getAmount();
}
```

```java
public interface ClaimRepository extends JpaRepository<Claim, Long> {
    @Query("SELECT c.id AS id, c.claimNumber AS claimNumber, c.status AS status, c.amount AS amount FROM Claim c")
    List<ClaimSummary> findAllSummaries();
}
```

Hibernate generates an exact column projection without instantiating entity proxies or tracking dirty states:

```sql
SELECT c.id, c.claim_number, c.status, c.amount FROM claims c;
```

## 5. Performance Comparison & Decision Matrix

| Strategy | Query Count | Memory Overhead | When to Choose |
| :--- | :--- | :--- | :--- |
| **Default Lazy (Naive)** | N + 1 | High (Many round-trips) | Avoid for collection listings |
| **Global Eager** | N + 1 or Cartesian product | Worst (Loads everywhere) | Never use on collections |
| **`@EntityGraph`** | **1** | Moderate (Full entity managed) | When entities need subsequent mutation or validation |
| **DTO Projection** | **1** | Lowest (No proxy tracking) | Read-only API listing and dashboard analytics |

In Claimora, pairing `@EntityGraph` for claim detail management with interface projections for summary feeds delivered a **~30% overall latency drop** and rock-solid p99 response times.
